# FRONTEND SECURITY AUDIT — PHASE 5

You are continuing a security audit of an ecommerce application.

The backend security baseline has already passed the final security gate.

Completed backend phases:

* CRITICAL #1 — Payment Webhook Security
* CRITICAL #2 — Inventory / Checkout Concurrency
* HIGH #1 — Authorization / IDOR
* PHASE 3 — Admin Authorization / Permission Bypass
* PHASE 4 — Price Manipulation / Business Logic Integrity
* Quick Backend Security Gate — PASS

The backend is now considered security-baseline complete.

Your task is:

# PHASE 5 — FRONTEND SECURITY AUDIT

==================================================
IMPORTANT SCOPE
===============

This task is ONLY for frontend security.

Do NOT:

* Modify backend code.
* Re-open completed backend security phases.
* Perform backend refactoring.
* Change backend API contracts unless absolutely required to fix a frontend integration issue.
* Start deployment hardening.
* Start performance optimization unless it creates a security issue.
* Automatically proceed to another phase.

First:

AUDIT → IDENTIFY → CLASSIFY → PLAN

Then:

FIX → TEST → VERIFY → REPORT

Do NOT modify code before understanding the frontend architecture.

==================================================

First inspect the frontend project.

Determine:

* Framework
* Build system
* Package manager
* Routing system
* State management
* HTTP/API client
* Authentication implementation
* Token storage
* User/session state
* Permission/role handling
* Form validation
* File upload handling
* Payment integration
* Error handling
* Environment configuration

Identify:

* src/
* components/
* pages/
* routes/
* services/
* api/
* hooks/
* stores/
* contexts/
* utils/
* auth/
* payment/
* admin/
* checkout/

Also inspect:

* package.json
* lock file
* environment files
* build configuration
* TypeScript configuration if applicable
* framework configuration
* API client configuration

DO NOT modify anything during this discovery phase.

==================================================
PHASE 2 — AUTHENTICATION SECURITY
=================================

Audit how authentication tokens are stored and handled.

Search for:

* localStorage
* sessionStorage
* cookies
* document.cookie
* Authorization
* Bearer
* accessToken
* refreshToken
* JWT
* token
* credentials
* auth headers

Determine:

1. Where access tokens are stored.
2. Where refresh tokens are stored.
3. Whether tokens are accessible to JavaScript.
4. Whether tokens are persisted unnecessarily.
5. Whether logout actually removes session credentials.
6. Whether expired tokens are handled correctly.
7. Whether refresh token rotation is handled safely.
8. Whether tokens are accidentally logged.
9. Whether tokens appear in URLs.
10. Whether tokens are included in analytics/error reporting.

Pay particular attention to:

```text
localStorage.setItem("token", ...)
localStorage.setItem("accessToken", ...)
localStorage.setItem("refreshToken", ...)
```

Do NOT automatically declare localStorage a vulnerability without understanding the application's architecture and threat model.

If a more secure HttpOnly/Secure/SameSite cookie architecture is already supported by the backend, document whether migration is appropriate.

Never expose:

* JWT
* refresh token
* payment secret
* API secret
* private key

in frontend source.

==================================================
PHASE 3 — XSS AUDIT
===================

Audit all user-controlled data rendered into HTML.

Search for:

* dangerouslySetInnerHTML
* innerHTML
* outerHTML
* insertAdjacentHTML
* eval
* Function(...)
* document.write
* v-html
* HTML injection libraries
* markdown renderers
* rich text editors
* URL-based rendering
* DOM manipulation

Identify user-controlled inputs such as:

* Product name
* Product description
* Review
* Comment
* User profile
* Address
* Coupon
* Search query
* URL query parameters
* Error messages
* Admin-entered content

Test payload:

```html
<script>alert(document.domain)</script>
```

Also test:

```html
<img src=x onerror=alert(document.domain)>
```

and:

```html
<svg onload=alert(document.domain)>
```

Expected:

* Payload is rendered as text OR safely sanitized.
* JavaScript MUST NOT execute.

If HTML rendering is genuinely required:

* Use a maintained sanitizer.
* Sanitize at the correct trust boundary.
* Do not implement an ad-hoc regex sanitizer.

==================================================
PHASE 4 — DOM / URL-BASED XSS
=============================

Audit data originating from:

* window.location
* location.search
* location.hash
* route parameters
* query parameters
* redirect URLs
* postMessage
* localStorage
* sessionStorage

Check whether these values are inserted into:

* HTML
* DOM
* URLs
* script contexts
* event handlers

Test malicious URLs such as:

```text
?search=<img src=x onerror=alert(1)>
```

and:

```text
?redirect=javascript:alert(1)
```

Never allow attacker-controlled redirect destinations without validation.

==================================================
PHASE 5 — ROUTE GUARDS / AUTHORIZATION UX
=========================================

Audit:

* Protected routes
* Admin routes
* User routes
* Guest routes
* Role checks
* Permission checks
* Route redirects

Examples:

```text
/admin
/admin/users
/admin/products
/admin/orders
/account
/orders
/checkout
```

Verify:

* Unauthenticated users cannot access protected UI.
* Non-admin users cannot access admin UI.
* Users cannot bypass guards by directly entering URLs.
* Expired sessions redirect appropriately.
* Logout invalidates frontend auth state.

IMPORTANT:

Frontend route guards are NOT a security boundary.

The backend remains authoritative.

Do not weaken backend authorization simply to make frontend routing work.

==================================================
PHASE 6 — CLIENT-SIDE BUSINESS LOGIC
====================================

Audit whether frontend calculations can incorrectly influence authoritative backend state.

Inspect:

* Product price
* Cart price
* Quantity
* Discount
* Coupon
* Shipping
* Tax
* Order total
* Payment amount

The frontend may calculate values for display, but the backend must remain authoritative.

Check requests such as:

```json
{
  "productVariantId": "...",
  "quantity": 1,
  "price": 1,
  "total": 1,
  "discount": 999999
}
```

If frontend sends fields that the backend ignores, this is not automatically a vulnerability.

Determine whether:

1. The field is actually used by backend.
2. The field can create inconsistent UI.
3. The field can mislead users.
4. The frontend incorrectly assumes client-calculated values are authoritative.

Do not duplicate backend business logic unnecessarily.

==================================================
PHASE 7 — PAYMENT FRONTEND SECURITY
===================================

Audit all payment-related frontend code.

Search for:

* VNPay
* MoMo
* paymentUrl
* paymentAmount
* amount
* orderId
* callback
* returnUrl
* redirect
* payment status

Verify:

1. Payment URL is received from trusted backend response.
2. Frontend does not construct payment URLs using secrets.
3. Frontend does not expose payment API secrets.
4. Frontend does not decide payment success solely from client state.
5. Frontend does not mark an order as paid locally.
6. Payment status is ultimately obtained from backend.
7. Return/callback query parameters are not blindly trusted.
8. Redirect URLs cannot be manipulated into open redirects.

A frontend route like:

```text
/payment/success
```

must NOT assume:

```text
?status=success
```

means the payment is actually successful.

The backend remains the source of truth.

==================================================
PHASE 8 — SENSITIVE DATA EXPOSURE
=================================

Search for secrets and sensitive data in:

* source code
* .env files
* public configuration
* build artifacts
* console.log
* console.error
* analytics
* error reporting
* Redux/state stores
* browser storage

Search patterns:

```text
API_KEY
SECRET
PRIVATE_KEY
PASSWORD
TOKEN
JWT
CLIENT_SECRET
DATABASE
CONNECTION_STRING
```

Frontend environment variables are NOT automatically secret.

Anything bundled into a browser application should be considered public.

Verify no frontend bundle contains:

* Payment provider secret
* JWT signing secret
* Database credentials
* Admin secret
* Private API key
* Internal service credentials

==================================================
PHASE 9 — LOGGING / ERROR HANDLING
==================================

Audit:

* console.log
* console.error
* debug logs
* API error messages
* stack traces
* server response display
* toast notifications
* error boundaries

Do not expose:

* JWT
* access token
* refresh token
* passwords
* payment secrets
* database errors
* internal stack traces

Example of unsafe behavior:

```javascript
console.log("Auth response:", response);
```

if response contains tokens.

Check whether sensitive errors are shown directly to users.

==================================================
PHASE 10 — INPUT VALIDATION
===========================

Audit all user input:

* Login
* Registration
* Search
* Address
* Checkout
* Coupon
* Review
* Profile
* Password
* File upload

Verify:

* Client-side validation exists where appropriate.
* Maximum lengths are enforced for UX.
* Unexpected input types are handled.
* Empty/null values are handled.
* Numeric values are validated.
* Negative quantities are prevented in UI.
* File types/sizes are validated.

IMPORTANT:

Frontend validation is for UX.

Do NOT assume it replaces backend validation.

Do NOT introduce validation that contradicts legitimate backend behavior without understanding the business rule.

==================================================
PHASE 11 — FILE UPLOAD
======================

If frontend supports file upload, audit:

* File type validation
* File extension validation
* MIME validation
* Maximum file size
* Multiple file upload
* Preview rendering
* Object URLs
* SVG handling
* Filename rendering

Special attention:

SVG files can contain active content.

Do not blindly inject uploaded SVG/HTML into the DOM.

Verify that uploaded content is treated according to the backend's upload/security model.

==================================================
PHASE 12 — OPEN REDIRECTS
=========================

Search for:

* window.location
* window.location.href
* location.assign
* location.replace
* router.push
* navigate()
* redirect
* returnUrl
* callbackUrl
* next
* redirectUrl

Check whether attacker-controlled values can cause:

```text
https://trusted-site.com/login?redirect=https://evil.example
```

Expected:

* Only trusted internal paths are accepted.
* External redirect destinations are explicitly allowlisted where necessary.

Test:

```text
?redirect=https://evil.example
```

Expected:

* Redirect is rejected or normalized to a safe internal route.

==================================================
PHASE 13 — POSTMESSAGE / CROSS-WINDOW COMMUNICATION
===================================================

If the frontend uses:

```javascript
window.postMessage
window.addEventListener("message", ...)
```

audit:

* origin validation
* message type validation
* payload validation
* trusted sender
* sensitive data transmission

Never use:

```javascript
if (event.data.status === "success") {
    markPaymentComplete();
}
```

without validating origin and backend payment state.

==================================================
PHASE 14 — DEPENDENCY SECURITY
==============================

Inspect:

* package.json
* package-lock.json
* yarn.lock
* pnpm-lock.yaml

Run the project's appropriate dependency audit.

For npm:

```text
npm audit
```

For yarn:

```text
yarn audit
```

For pnpm:

```text
pnpm audit
```

Use the package manager actually used by the project.

Do NOT blindly upgrade every dependency.

For each vulnerability determine:

* Severity
* Package
* Direct/transitive
* Exploitability
* Whether the vulnerable package is used in production
* Safe upgrade path
* Potential breaking changes

Only apply dependency changes that are necessary and safe.

==================================================
PHASE 15 — ENVIRONMENT / BUILD SECURITY
=======================================

Inspect:

* .env
* .env.local
* .env.production
* .env.example
* build configuration

Determine:

* Which variables are public.
* Which variables are secrets.
* Whether production configuration leaks development endpoints.
* Whether localhost URLs are used in production.
* Whether debug mode is enabled.
* Whether source maps expose sensitive information.
* Whether API base URL is configurable safely.

Remember:

Frontend environment variables embedded in the bundle are PUBLIC.

Never place secrets in them.

==================================================
PHASE 16 — API CLIENT SECURITY
==============================

Audit the HTTP client/interceptors.

Check:

* Authorization headers
* Token refresh
* Retry behavior
* 401 handling
* 403 handling
* Error parsing
* Request logging
* Sensitive request logging
* Duplicate requests
* Credential handling

Verify that a failed refresh does not create an infinite loop.

Example:

```text
API → 401
   ↓
refresh token
   ↓
401
   ↓
refresh again
   ↓
infinite loop
```

Expected:

* Refresh failure terminates the session safely.
* User is redirected to login.
* No infinite retry loop.

==================================================
PHASE 17 — SECURITY HEADERS / FRONTEND DEPLOYMENT CHECK
=======================================================

Inspect whether the frontend deployment has mechanisms for:

* Content-Security-Policy
* X-Content-Type-Options
* Referrer-Policy
* Frame protection
* HTTPS
* Secure cookies if applicable

Do not modify server infrastructure unless the project explicitly includes frontend deployment configuration.

If headers are controlled outside the repository:

Document them as deployment findings.

Do NOT block frontend application fixes on infrastructure changes.

==================================================
PHASE 19 — FIX
==============

After the audit:

Implement minimal safe fixes.

Priorities:

1. Critical
2. High
3. Medium
4. Low

Do not introduce unnecessary architecture changes.

Do not duplicate backend security logic.

Do not move secrets into another frontend file and call it fixed.

Do not solve XSS with fragile regex.

Do not disable security controls to make tests pass.

==================================================
PHASE 20 — TESTING
==================

Create or update frontend tests using the project's existing framework.

At minimum, test applicable cases:

### Authentication

* Unauthenticated user cannot access protected route.
* Logout clears auth state.
* Expired token is handled.
* Failed refresh terminates session safely.

### Authorization UX

* Normal user cannot access admin UI.
* Admin UI is hidden/protected appropriately.
* Direct URL navigation is guarded.

### XSS

* Product/review/user content is safely rendered.
* Malicious HTML does not execute.

### Open Redirect

* External redirect is rejected.
* Internal redirect works.

### Payment

* Frontend does not mark payment successful solely from URL/query parameters.
* Payment state comes from backend.
* Malicious payment parameters do not change order state.

### Sensitive Data

* Tokens are not logged.
* Secrets are not embedded in frontend source.
* Sensitive API responses are not exposed unnecessarily.

### Input Validation

* Invalid quantity rejected at UI level.
* Invalid fields handled safely.
* File upload constraints work if applicable.

==================================================
PHASE 21 — ADVERSARIAL TESTING
==============================

Act as an attacker.

Attempt:

1. Inject HTML into product/review/profile fields.
2. Inject JavaScript through query parameters.
3. Modify localStorage auth state.
4. Modify client-side price.
5. Modify client-side total.
6. Modify payment status query parameters.
7. Change order IDs in frontend routes.
8. Access /admin directly.
9. Manipulate redirect parameters.
10. Trigger refresh-token loops.
11. Upload malicious file types.
12. Send malformed API responses where practical.
13. Modify Redux/store/context state through browser tools.
14. Attempt to bypass UI restrictions.

IMPORTANT:

Changing frontend state is expected to be possible.

The question is:

"Does changing frontend state cause an unauthorized or insecure backend action?"

Do not classify client-side state manipulation alone as a backend authorization vulnerability because backend authorization has already been audited.
